Work Item Handler Public API Migration

Repository: apache/incubator-kie  ·  Modules affected: kogito-api, kogito-jbpm  ·  API stability tier: public stable

1. Why This Was Necessary

BAMOE v9 exposes a Custom Work Item Handler extension point that lets application developers plug arbitrary Java logic into BPMN Custom Task and Service Task nodes. However, every type a handler author needed to import — the handler interface, work item, manager, transition, and lifecycle objects — lived in one of two "internal" locations:

org.kie.kogito.internal.process.workitem.*
kogito-api — "internal" sub-package
+
org.kie.kogito.process.workitems.impl.*
kogito-jbpm — "impl" sub-package
+
org.kie.kogito.process.impl.*
kogito-jbpm — config "impl" sub-package
The problem: The internal and impl sub-package naming convention is the Java ecosystem's standard signal — used by the JDK itself with sun.* and com.sun.internal.* — that types are not part of a guaranteed, versioned API contract. They can change signature, move, or be removed between releases without a deprecation cycle. Any application team importing these types accepts an invisible upgrade risk.

The concrete impacts on application teams were:

  • Handler authors had to import 10+ types from internal.* packages just to write a single handler class.
  • The only officially public type on the registration side was the WorkItemHandlerConfig interface; the implementation class (CachedWorkItemHandlerConfig) required importing from process.impl.
  • The base class (DefaultKogitoWorkItemHandler) required importing from a kogito-jbpm internal module — creating a transitive dependency on engine internals.
  • Documentation could not accurately describe the correct public imports, causing confusion and incorrect code samples.

Layer 2 — Deprecated shims in org.kie.kogito.internal.process.workitem

Every original file in the internal package was replaced with a thin deprecated subtype that extends or implements the corresponding new public type. Existing code that imports the old package compiles with a @Deprecated(since="9.1", forRemoval=true) warning — no hard break.

Layer 3 — Deprecated shims in org.kie.kogito.process.workitems.impl

DefaultKogitoWorkItemHandler, DefaultWorkItemLifeCycle, DefaultWorkItemLifeCyclePhase, and DefaultWorkItemTransitionImpl now each extend the new public class, delegating all construction via super().

Layer 4 — Deprecated shims in org.kie.kogito.process.impl

CachedWorkItemHandlerConfig and DefaultWorkItemHandlerConfig now extend the new public CachedWorkItemHandlerConfig from kogito-api.

Layer 5 — Internal framework import updates

All internal.* and workitems.impl.* references were replaced with the new public package in every production and test source file across:

  • kogito-api — SecurityPolicy, KogitoProcessEventSupport, ProcessInstance, Process, ProcessService, runtime interfaces
  • kogito-jbpm/jbpm-flow — LightWorkItemManager, AbstractProcess, AbstractProcessInstance, event support implementations, and all other files in the module
  • kogito-jbpm/process-workitems — all builtin handlers (SystemOutWorkItemHandler, ServiceTaskHandler, SendTaskHandler, etc.) and KogitoDefaultWorkItemManager
  • kogito-jbpm/jbpm-usertask-workitem — UserTaskKogitoWorkItemHandler, Policies, UserTaskKogitoWorkItemHandlerFactory
Layer 6 — Corrections to builtin handlers that leaked internal field access

SystemOutWorkItemHandler directly accessed the workItemLifeCycle protected field from the old base class. It was corrected to use the inherited handler.completeTransition() and handler.abortTransition() public API methods, which also makes the code simpler.

4. Backward Compatibility Strategy

No hard break for existing clients. Every old type remains on the classpath. Existing code that was already importing internal.* or impl.* types will continue to compile unchanged — only with @Deprecated warnings guiding the migration.

The strategy applied to each category:

Old typeShim techniqueCompiles without change?
Interfaces (Handler, WorkItem, Manager, Transition, Policy, Lifecycle types)Empty interface Foo extends new.package.Foo {}Yes
Extendable classes (exceptions, WorkItemPhaseState)class Foo extends new.package.Foo { /* delegate constructors */ }Yes
Enum WorkItemTerminationTypeNon-extendable; replaced with final class forwarding static constants to the new enumYes
Impl base classes (DefaultKogitoWorkItemHandler etc.)class Foo extends new.package.Foo { /* delegate constructors */ }Yes
Config classes (CachedWorkItemHandlerConfig)Empty class Foo extends new.package.Foo {}Yes

The removal timeline follows the standard deprecation cycle: shims carry @Deprecated(since="9.1", forRemoval=true). They will be deleted in a future major release, at which point clients must have updated their imports.

7. BAMOE_v9_Extension_Points_Catalog.md Update

The catalog document (BAMOE_v9_Extension_Points_Catalog.md) was also updated as part of this work to:

  • Correct the wrong import paths that were previously listed (the catalog showed org.kie.kogito.process.workitem.* without internal, which did not match the actual source).
  • Add a per-import stability table annotating each import as ✅ public or ⚠️ internal.
  • Add the implements WorkItemHandlerConfig clause to the registration bean examples so the declared type is the public interface.
  • Document the upstream gap and the three proposed changes — which this implementation now delivers.

8. Migration Guide for Existing Handler Authors

  1. Replace imports — find any import beginning with org.kie.kogito.internal.process.workitem. or org.kie.kogito.process.workitems.impl. and change the package segment to org.kie.kogito.process.workitem.
  2. Update the config class — replace extends DefaultWorkItemHandlerConfig or extends CachedWorkItemHandlerConfig from org.kie.kogito.process.impl with extends CachedWorkItemHandlerConfig from org.kie.kogito.process.workitem.
  3. No logic changes required — all method signatures, constants, and behavior are identical in the new public package.
Tip: A single IDE refactor (Find & Replace in project scope) handles the entire migration in seconds. The compiler's deprecation warnings on the old imports serve as the exact checklist of what still needs updating.
